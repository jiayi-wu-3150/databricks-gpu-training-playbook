Default to AI Runtime

  • Databricks' own guidance, quoted: for GPU deep learning, fine-tuning and batch inference, "Databricks recommends AI Runtime ... instead of Runtime ML"
  • Cited reasons: lower total cost of ownership, a more flexible developer experience, multinode scale
  • Classic remains the right answer in specific cases: account separation, Spark in-cluster, Ray-on-Spark, GPU types AI Runtime lacks, or an unsupported compliance profile
  • See the appendix for the full decision list

GPU concepts: the vocabulary

  • Single-node, single-GPU: where every project should start
  • Single-node, multi-GPU: one machine, several GPUs, data-parallel
  • Multi-node: several machines, GPUs synchronizing over the network
  • Data parallelism (DDP): replicate the model on each GPU, each reads a different data shard, compute gradients, average gradients across all GPUs, update, repeat
  • The concepts are durable. Only the tooling churns.
GPU concepts: the vocabulary5 / 41

Why the interconnect is the ceiling

  • Gradient averaging is a collective operation (ring all-reduce) on every single step
  • Each GPU sends gradients to a neighbour and receives from another, around a logical ring
  • So at scale the network, not the GPU, becomes the bottleneck
  • This is why multi-node training is sensitive to the fabric, and why RDMA-class interconnect is a real differentiator rather than a marketing bullet
  • It is also why you climb the scaling ladder in order instead of jumping to multi-node
Why the interconnect is the ceiling6 / 41

The scaling ladder

  • 1. Single node, single GPU: establish a correct, reproducible baseline
  • 2. Fix the data pipeline if it is the bottleneck. It often is (see our measured results)
  • 3. Single node, multi-GPU
  • 4. Multi-node
  • 5. Hyperparameter search, only once the baseline is stable
  • Distributed code is harder to debug and can be slower from communication overhead. Distribute when the model or data will not fit, not by default.

The training lifecycle on Databricks

  • Data (UC Volumes / Delta) -> Train (GPU compute) -> Track (MLflow) -> Register (Unity Catalog) -> Deploy (Model Serving or export off-platform)
  • Governance runs through the entire chain: the data, the experiment, the model, and the lineage between them all live in Unity Catalog
  • That is the part a bare GPU cluster somewhere else does not give you
  • The deck is organized along this lifecycle; the runtime is a swappable parameter

Job compute vs all-purpose compute

  • Job compute for recorded runs: cheaper DBUs, terminates automatically, spec lives in code
  • All-purpose only for the interactive debug loop, where a warm cluster turns a 6-minute iteration into seconds
  • Methodological point: AI Runtime is ephemeral per-run compute. Job compute is the honest comparison, because it also pays its start cost every run
  • Timing classic on a pre-warmed all-purpose cluster hides the 10-minute spin-up
  • NCCL escapes: NCCL_P2P_DISABLE=1 for peer-access errors on G5; NCCL_SOCKET_IFNAME=eth0 for multi-node NCCL failures

Two things to know about the data path

  • Mosaic Streaming appears NOWHERE in the AI Runtime docs. The runtimes genuinely have different recommended data paths. This is not the same script with a different compute target.
  • File sizing matters: aim for 1 to 10 GiB files. For many small files, copy in parallel first.
  • Our own measured ViT gap turned out to be a data-pipeline effect, not a GPU effect
  • Checkpointing on AI Runtime: PyTorch Distributed Checkpoint, dcp.save / dcp.load with UCVolumeWriter and UCVolumeReader. NOT torch.save.
  • Always checkpoint. There is no capacity SLA.
  • Under /Volumes/{cat}/{schema}/, every first-level directory must be a registered volume or os.makedirs fails with OSError errno 95

Techniques: tracking and registration

  • Set the experiment explicitly. AI Runtime derives one from experiment_name; classic .py tasks get none at all and fail with 'Could not find experiment with ID None'
  • HuggingFace Trainer: report_to=['mlflow']. Lightning: mlflow.pytorch.autolog()
  • AI Runtime auto-logs GPU/CPU/memory system metrics and run logs (60-day retention). Classic does not do this automatically.
  • Log metrics from rank 0 only in distributed runs
  • Register to UC: mlflow.set_registry_uri('databricks-uc'), name as catalog.schema.model. A signature is required.
Techniques: tracking and registration15 / 41

The model-logging trap

  • mlflow.pytorch.log_model fails on an Accelerate/AMP-prepared model: PicklingError: Cannot pickle a prepared model with automatic mixed precision
  • And bf16 weights break signature inference: Input type (float) and bias type (BFloat16) should be the same
  • Fix, three lines:
m = trainer.accelerator.unwrap_model(trainer.model)
m = m.to('cpu').to(torch.float32).eval()
mlflow.transformers.log_model(transformers_model={'model': m, 'tokenizer': tok}, ...)
  • For LoRA, log the MERGED fp32 model, not the adapter, if it must load without PEFT

Pin versions; distrust some docs

  • The two runtimes ship a DIFFERENT MAJOR VERSION of transformers: 5.8.1 on AI Runtime v6 versus 4.57.1 on DBR 18 ML
  • Also torch 2.11 / CUDA 13.0 versus torch 2.9 / CUDA 12.9
  • Code is not guaranteed to move between them unpinned. Pin explicitly rather than relying on preinstalled defaults.
  • Good news: peft and trl pinned to the same versions installed cleanly on both
  • Stale docs to expect: the public compute/gpu page still claims CUDA 11.0 while DBR 17.3+ ships 12.6+; train-model/pytorch pins torch==1.5.0 in its example; dl-best-practices never mentions AI Runtime at all

Unvarnished truths: AI Runtime (1 of 2)

  • No capacity SLA and no startup SLA. On a capacity miss the session sits in 'starting' then fails, with no durable queue. Checkpoint and retry with backoff.
  • Cross-region bursting is real and not pinnable. The Geo setting enforces Geo, not region.
  • No customer-configurable GPU or spend caps, and no reserved capacity today.
  • No self-service off switch post-GA.
  • Access control is coarse: serverless ACLs are per-object (Interactive / Automated), NOT per-GPU. You cannot express 'GPU training only'.
Unvarnished truths: AI Runtime (1 of 2)19 / 41

Unvarnished truths: AI Runtime (2 of 2)

  • Notebook @distributed is single-NODE. Multi-node requires the CLI plus torchrun.
  • 1xA10 and 1xH100 are single-GPU. Multi-GPU needs 8xH100 or 8xB300.
  • 1xH100 is not a valid serverless GPU JOB config. Use 1xA10 or 8xH100.
  • for_each is unsupported, and dynamic {{}} references do not work in ai_runtime_task.
  • Default quota: 8 nodes x 8xH100 = 64 GPUs per workspace.
  • Compute runs in the Databricks-managed plane. This cannot satisfy a cloud-account-separation requirement; no customer-hosted variant exists.
Unvarnished truths: AI Runtime (2 of 2)20 / 41

Unvarnished truths: classic GPU

  • About 10 minutes to a usable GPU, every single run
  • Idle clusters bill. Auto-terminate is the only guard, and the defaults are generous.
  • Spot GPUs are hard to retain; quota increases are often needed
  • Photon does not apply to GPU instance types
  • No automatic system-metrics capture into MLflow
  • The honest upside: compute runs in your own cloud account, and the runtime is genuinely batteries-included. Our ViT run needed ZERO added libraries.

Tune where the evidence points

  • Our own measurements located the bottleneck: the ViT gap between runtimes was 26.9%, but the LoRA gap was only 2.7%. Same GPU both times.
  • That difference is the data pipeline, not the GPU. ViT decodes and preprocesses JPEGs on the host every batch; LoRA feeds pre-tokenized text and is GPU-matmul-bound.
  • So for image and video work, profile the input pipeline BEFORE buying a bigger GPU.
  • The most obviously untapped knob in our own runs: LoRA peaked at 4.99 GB on a 23 GB card. Batch size could rise roughly 4x before OOM. That is free throughput we left on the table.
  • Measure, change one knob, measure again. Single cold runs mislead.

Notes on the multimodal examples

  • The VLM example is real but large: Nemotron Super VL at 120B needs 8xH100. It will not fit on an A10. Plan the accelerator before promising a demo.
  • Diffusion is the genuine gap. There is no Stable Diffusion, SDXL, Flux, DreamBooth, LoRA-on-SDXL or ControlNet example anywhere in the cookbook or the docs tutorials.
  • diffusers is also not in the preinstalled stack, so it would need declaring as a dependency.
  • If asked 'can we fine-tune an image generator here': yes technically, but there is no reference implementation to point at, and that should be said plainly.
  • Multimodal data loading genuinely differs from both pure-vision and pure-text: the processor handles interleaved image and text, so collation and sequence budgeting change.

What that table actually means

  • The direction FLIPS by workload. So 'classic compute is faster per step' is not a true statement, and neither is the reverse.
  • The most likely driver is the library version gap, not the platform: AI Runtime ships transformers 5.8.1 and torch 2.11; classic ships 4.57.1 and torch 2.9. Qwen2-VL support improved substantially across that major version.
  • So AI Runtime wins where the newer stack helps, and loses where host-side data loading dominates.
  • Honest statement: per-step throughput depends on YOUR workload and YOUR library versions, not on serverless versus classic. Pin versions and measure your own workload.
  • End-to-end, serverless still wins on anything short, because of the 621-second provisioning.
What that table actually means31 / 41

Multimodal data loading is different

  • Confirmed by building it. A VLM sample needs:
  • 1. Chat-template messages carrying an image placeholder
  • 2. Text and images through ONE processor call together
  • 3. A custom collator. The stock text collator cannot do this.
  • 4. Masking image-placeholder and pad tokens out of the loss
  • 5. Sequence budgeting for image tokens, which dominate the text (max_pixels)
  • 6. remove_unused_columns=False, or Trainer strips the image column before collation
  • Freezing the vision tower and adapting only the language projections gave 0.197% trainable, an order of magnitude below the text-only LoRA's 1.75%.
  • Portability: the VLM model class moved between transformers majors. The template tries Qwen2VLForConditionalGeneration and falls back to AutoModelForVision2Seq.
Multimodal data loading is different32 / 41

Read three things off those tables

  • 1. Serverless is 4.7x to 5.7x faster END TO END on short work, almost entirely because of cluster provisioning (621 s, measured identically on two separate job-compute runs).
  • 2. Per-step throughput has no consistent winner. It flips by workload and tracks the library versions, not the platform. Measure your own workload.
  • 3. Training is equivalent across runtimes: losses match to 3-4 decimal places, peak memory matched exactly on the VLM, and the VLM produced identical generated text, all across different transformers major versions.
  • Headroom: a 0.5B text model peaked under 5 GB, and a 2.2B VLM under 6.4 GB, on a 24 GB A10. You do not need H100s to start.
  • Caveat stated plainly: single cold runs, n=1 per cell. Directional, not benchmarks.

Getting the model out

  • Relevant whenever inference must run somewhere other than Databricks: on-prem, at the edge, or in your own cloud account.
  • The honest framing: this path is THINLY DOCUMENTED. The model-lifecycle page presents download_artifacts as an advanced/debug use case, and the Model Serving docs contain no export or on-prem guidance at all.
  • What works today:
mlflow.artifacts.download_artifacts(
artifact_uri='models:/cat.schema.model/1', dst_path='/Volumes/.../export')
  • Use /Volumes destinations. /dbfs paths fail.
Getting the model out34 / 41

Model export: what to watch for

  • For LoRA, log the MERGED fp32 model, not the adapter, so it loads anywhere with plain transformers and no PEFT dependency.
  • Set an explicit ModelSignature, or downstream loaders have no contract.
  • Known risk: an unresolved report of ONNX artifact download failing with OSError errno 95 to /Volumes, while non-ONNX flavors worked. ONNX is the obvious edge format, so test it for your own case rather than assuming.
  • UC access control and lineage do NOT follow the exported artifact. Governance stops at the boundary.
  • MLflow artifact reads are slow for large checkpoint sets.

Notes on the serverless boundary

  • This applies to ALL serverless compute, not just GPU. The same plane runs CPU notebooks and jobs.
  • Available mitigations: Geo enforcement, NCC / PrivateLink / egress controls, and keeping all data and checkpoints in UC Volumes
  • Residual risks a reviewer can legitimately still raise: managed compute-plane ownership; unpinnable cross-region placement; Geo-level-only residency; transient GPU-host data with no published wipe SLA; the isolation whitepaper not being public
  • FedRAMP High and DoD IL5 are documented as unsupported. Do not assert FedRAMP Moderate coverage without written confirmation.

When classic is the right answer

  • Cloud account separation is required. This is the decisive case.
  • Spark and GPU needed in the SAME cluster
  • Ray-on-Spark, which is not available on serverless
  • A library AI Runtime does not carry
  • GPU types AI Runtime lacks: T4, L4, L40S, A100, V100
  • A compliance profile AI Runtime does not cover
  • Very long training runs where per-step throughput outweighs a 10-minute start. Our measured crossover was roughly 46 minutes of training-loop time (n=1, directional).

The four costliest gotchas

  • 1. environment.version: 6 silently gives an image with NO torch. Use 'databricks_ai_v6'.
  • 2. AI Runtime auto-retries deterministic failures. Set max_retries: 0 while developing.
  • 3. mlflow.pytorch.log_model plus AMP/Accelerate equals PicklingError. Unwrap and cast to fp32.
  • 4. Classic .py tasks have no implicit MLflow experiment. Set it in the script.
